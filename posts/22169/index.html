【 Wireshark／網路實務 】 - 02：TLS 握手與憑證

發表於 2026-01-20 更新於 2026-07-11 分類於 網路 Disqus：
文章字數： 1k 所需閱讀時間 ≈ 1 分鐘
以實務分析角度理解 TLS 的角色、握手流程、憑證驗證與 Wireshark 觀察重點。

前言

TLS 是 HTTPS 與許多加密服務的保護層。分析 TLS 時，重點不是嘗試「看懂所有加密後內容」，而是從握手、憑證、SNI 與連線行為判斷：這條連線是否符合預期、是否使用合理的加密設定，以及是否出現值得追查的異常。

你會得到什麼

  • 分辨 TCP、TLS 與 HTTP 在連線中的分工。
  • 讀懂 TLS 握手中可見的基本資訊。
  • 用 Wireshark 先找出可疑連線，再決定是否需要更深入蒐證。

1. TLS 在網路堆疊中的位置

以一般 HTTPS 連線為例，IP 負責傳遞封包、TCP 負責可靠傳輸，TLS 則在 TCP 之上建立加密與身分驗證通道；HTTP 才在 TLS 通道內傳送。這表示封包擷取工具通常仍能看到 IP、TCP 與 TLS 的連線資訊，但看不到已加密的 HTTP 內容。

2. 最小可用的握手模型

握手細節會依 TLS 版本而不同，但可先用下列模型理解：

  1. 用戶端提出可接受的 TLS 版本、密碼套件與延伸資訊。
  2. 伺服器選擇設定並回傳憑證，讓用戶端驗證伺服器身分。
  3. 雙方建立工作階段金鑰，後續應用資料改以對稱式加密傳送。

分析時可先確認三件事：連線目標是否合理、憑證名稱是否對得上網域、協商出的版本與套件是否符合組織基準。

3. 憑證驗證不只看「有沒有鎖頭」

瀏覽器顯示安全連線，代表它完成了當下的驗證；調查時仍應比對憑證的主體名稱、簽發者、有效期限與實際連線的主機名稱。名稱不符、憑證過期、非預期的簽發者，或同一程式短時間連往大量不同網域，都是應進一步確認的訊號，而非單獨定罪的證據。

4. Wireshark 的實務起點

先以篩選器縮小範圍，再回到程序與時間線交叉驗證：

  • tls.handshake：觀察 Client Hello、Server Hello 與憑證交換。
  • tcp.port == 443：找出常見 HTTPS 流量，但不要把 443 視為 TLS 的唯一埠號。
  • ip.addr == ...：將封包與已知主機或事件時間線關聯。

5. 分析限制與下一步

未持有工作階段金鑰時，TLS 的應用資料通常無法直接解密；這是設計目的，不是工具失效。應結合 DNS、端點程序樹、代理伺服器日誌與憑證資訊，建立行為證據鏈。若是自有測試環境，再依組織流程蒐集可供解密的診斷資料。

結論

TLS 分析的價值在於辨識「加密連線的行為與身分」，而不是繞過加密。先建立 TCP → TLS → 應用協議的分層觀念，再把握手與端點證據關聯，才能避免只看見加密流量就停止分析。
